# PR449: primary Mermaid community feedback and implementation decisions

Research date: 2026-10-22. This is a research note, not a new benchmark or renderer change. Primary issue bodies, review discussions and maintainer replies were fetched through the connected GitHub tools. A retrievable copy, without HTML or signed image URLs, is in [community-primary-evidence.json](community-primary-evidence.json). Mutable issue status is reported as retrieved; a closed issue is not proof that a shipped version fixes every reproducer. Revision-specific third-party numbers below remain the reporters' measurements.

The starting context was `docs/mermaid-community.json`, `docs/design/system/layout-qualification.md` and `docs/design/system/layout-community-comparison.md` in `/workspace/agentic-mermaid`. These already separate the 83 provenance nodes from distinct algorithms, owned solver versus whole public renderer, and published distributions versus current source. Preserve those distinctions. Pele and Ondine share layout ancestry; two implementations do not make two independent validations of a heuristic.

## What the feedback changes

The strongest additional signal is that users want predictable, meaningful output before they want a universally clever engine. Several sources specifically support subtraction: stop re-centering labels after routing; stop optimizing already valid geometry without checking its reserved space; prune unused diagram implementations; avoid repeating whole layouts unless a bounded quality gain justifies it. Other sources show the limit of subtraction: dropping port sides, local directions, labels, or relationships merely makes the drawing easier by changing what it means.

Our existing qualification says we still lose Architecture crossings, ER foreign-shaft/label conflicts, individual bend/area cases, edit stability, some time/allocation ceilings and full paint qualification. These reports explain why those remain practical product defects. They do not demonstrate that another engine has solved them universally, or that ours matches ELK. In particular, ELK's own issue tracker contains compound ordering, fixed-node routing and label interactions.

## Subtraction and family-scope decisions worth testing first

1. **Remove post-routing damage before adding optimization.** ER label routing and final straightening should have one reservation owner. A change is kept only after completed-paint clearance; an unchanged safe route is a valid optimum under a work budget.
2. **Bound Architecture candidates by feasibility and visible improvement.** Diagnose contradictory side/grid constraints early; add global boundary order hints once. Avoid laying out the entire graph repeatedly without a measured failure witness. Preserve Architecture as experimental/opt-in if its full ten-source cohort still loses crossings.
3. **Prune candidate passes, not authored meaning.** Try one placement, one legal route and one repair budget. Measure which later passes repair earlier damage, which improve crossings at unacceptable area/bend cost, and which consume work while losing selection. Failed ablations must remain in the report.
4. **Evaluate narrow admission without narrowing the denominator.** A Flowchart-only default policy may improve quality and save setup work, but unchanged ER/Architecture outputs then come from ELK and remain visible as fallbacks. Report mixed-policy results by family and backend; do not credit an ELK render as a native win. Keep six-family strict mode for development.
5. **Evaluate adding families only when their structure fits.** Existing diagram coverage, parser availability or shared model representation is insufficient. Sequence, Gantt, timelines, pies and charts have family-specific ordering/coordinate contracts and should not become layered-graph experiments merely to increase coverage. State needs marker semantics, composite regions and transitions; Class/ER need sized member/cardinality geometry. An independent family can still benefit from build-time selection without sharing the engine.
6. **Separate less code delivered from less code executed.** Merman's family selection and Ondine's [per-family compiler policy](https://github.com/wevm/ondine/blob/0b589ec34481856b4153526f10a0a35558a201a8/AGENTS.md) support both static subsets and an opt-in compiler; neither a mount-only runtime nor a native executable measurement ranks our full browser closure.

## Ideas to reject or keep explicitly unproven

- Do not silently ignore local direction because another lightweight implementation does; our owned contract is stricter. A documented quality concession in Zombie is a product choice, not evidence that users accept the same concession here.
- Do not force source order globally. Users request stable source order, but other users need crossing reduction; ELK1091 shows that merged/labelled edges complicate that trade-off. Prefer explicit constraints, stable tie-breaks and visible conflict/decline reasons.
- Do not convert all end labels into graph nodes without measuring dummy growth, port order, memory and compounds. Nor should midpoint labels be moved after routing without their reserved space.
- Do not replace authored edges with dummy junctions in the semantic model merely to satisfy a layout grid. Internal routing supports are acceptable if receipts and output still represent exactly the original relationship.
- Do not mistake a green screenshot baseline for correctness. Zombie [issue1592](https://github.com/dfadler/zombie-mermaid/issues/1592) correctly proposes topology/direction/labels/shape/order fidelity axes, but it is an AI-generated audit proposal, not an executed survey or proof. Keep semantic witnesses and unverified paint cases in the denominator.
- Do not treat a new engine or whole rewrite as the remedy for unprofiled overhead. Zombie [issue2144](https://github.com/dfadler/zombie-mermaid/issues/2144) describes ambitious speed/size rewrite targets, not achievements. Mermaid4697 supplies a concrete already-integrated example of useful subtraction.
- Do not claim universal ELK superiority or infer peer quality from throughput alone. We have community counterexamples against ELK and community examples where ELK improves other engines. PR449 must win or match each declared metric on its own pinned, retained population.

## Suggested experiment order and success criteria

| Priority | Experiment | Keep the change only if |
| --- | --- | --- |
| P0 | Remove label re-projection/straightening after reserved-route generation; preserve or locally repair labels | ER foreign-shaft conflicts improve, no authored relationship/side/label is lost, no new paint conflict, source and generated regressions remain accounted for. |
| P0 | Trace Architecture constraint feasibility and boundary order across projection → placement → side-constrained final routing | Every failed case identifies the first violated invariant; deterministic explicit decline is preferable to a semantically different success. Crossings, bends, area, time and allocation are all reported. |
| P1 | One candidate versus current retries versus bounded candidate search | Extra candidates have measurable selected quality benefit sufficient for their own time/allocation; no headline aggregate hides a losing family or input. |
| P1 | Dispatch: Flowchart-only, Flowchart+qualified State, six-family | Full population reports strict success and actual fallback separately; browser request graph and end-to-end effects are measured per policy, not estimated from engine size. |
| P1 | Editing: delete decision, add unrelated node, whitespace-only edit, expand/collapse compound, undo | Unchanged branch meaning/order, explicit port order and semantic fingerprints survive; raw/aligned motion and route changes improve without sacrificing safety. |
| P2 | Distribution subset and duplicate-work ablations | Consumed public outputs/receipts remain equivalent, emitted byte/request reductions are observed, and reductions are distinguished from native heap or warm-solver time. |
