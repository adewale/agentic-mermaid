# Independent review of PR449 attribution profiles

Reviewed `profile-worker.mjs`, `summarize-profiles.mjs`, job/manifest metadata, summary and raw CPU/heap trees from all 20 workers. This review only reads/analyzes existing data; no new render workloads, tests, builds or renderer edits were run.

## Overall assessment

The profiles are useful **diagnostic evidence**, with meaningful repeated hotspots. They are not paired timing qualification or proof of a counterfactual speedup. Fresh processes, explicit backend/fallback, cache switches before import, independent CPU/heap workers, complete per-call UTF-8/hash consumption, explicit receipt arms, collected-object inclusion flags, unchanged-output checks and preserved raw trees are sound choices.

The strongest result is more specific than “cyclic search allocates too much”: on cyclic18, repeated route-repair crossing queries account for much more sampled allocation than cycle-search scoring. On warm cached inputs, drawing, request preparation and SVG inspection remain substantial even when positioning is cheap.

## Methodological issues to preserve in reporting

1. **Large CPU-profiler start boundary.** Every CPU profile begins with a long first delta attributed to Node inspector `post`, from about 58 to 321 ms. This is before `windowStart`, and contributes about 3–15% of the reported sampled duration. In cyclic18 repeat, the first delta is 320,726 µs and `post` is 14.85%. Do not call this renderer work or multiply all profile fractions by `observedWindowMs`. Preserve raw-total fractions, or additionally report explicitly renderer/workload-conditioned attribution with the excluded denominator stated. Do not merely delete every `post` frame indiscriminately; identify the first boundary and retain accounting.
2. **The `normal` job label is an explicit diagnostic configuration.** Worker enables `text-spans,position-cache`; the source default also enables `indexed-layout`. This differs from an unqualified production-default configuration. The pinned package may implement some paths differently, so preserve the exact startup flags and do not imply these are current release-default profiles. It is valid to profile a known qualified configuration if labelled precisely.
3. **Five warmup calls do not establish steady state.** Cyclic15 CPU calls change from 6 to 13 across repeats, while GC fraction changes from 14.8% to 3.0%. Flow5 goes from 213 to 255 calls; ER has only one CPU observation per backend. These effects prevent timing ratios, receipt-overhead estimates and exact speedup claims. The repeated location of a hotspot is more credible than the observed throughput or GC fraction.
4. **Unequal window call counts and overshoot.** CPU/heap duration windows include completed calls, with potentially substantial final-call overshoot for slow cases. Normalize sampled byte estimates by completed calls only as an advisory figure; do not compare raw totals as if workloads were equal. Sampling and GC themselves can change call counts and object lifetimes.
5. **Source positions identify frame starts.** Source-map conversion is sensible and preserves generated keys. A large `layoutLayeredGraph` frame does not identify the expensive statement; CPU position ticks or narrower instrumentation are needed. `topInclusive` overlaps heavily and cannot be summed. Deduplication of repeated frame identities along a sampled stack correctly avoids double-counting that same aggregated frame's inclusive time, but it also removes recursion-depth information. Keep raw trees for ancestry.
6. **Coverage is intentionally narrow.** Sequence SVG is ELK-selected while its receipt arm is agentic-selected, and there is no agentic SVG sequence arm. Since that family's implementation is shared, it is a useful pipeline indication, but not a perfectly matched receipt experiment. No ELK heap profile exists for cyclic18 or warm flow/ER. Do not infer their allocation ratios to ELK from this set. Only four selected agentic profiles repeat.
7. **Memory/CPU metadata are endpoints, not window deltas or peaks.** `cpuUsage()` is cumulative since process start; `memoryUsage()` is after profiling stops and before/around report writing. Neither is an isolated render-window CPU measure or peak-memory result. `importMs` covers only the dynamic package import after worker dependencies load, not CLI startup-to-first-use latency.
8. **Sampling semantics are stated correctly.** Heap sampling requests both major/minor collected-object inclusion and fails rather than silently dropping flags; this is valuable for short-lived churn. It remains an estimate, not exact total allocation or retained/peak heap. Support in the pinned Node/V8 protocol, sampling interval and raw sample count should remain in the archive. Hashing/encoding is included intentionally; it belongs to this public-consumption contract, though its frames can be reported separately.

Phrase the finding precisely: full receipt materialization is avoided; all contract preparation is not. This is a better target for profiling than claiming the SVG path serializes a full receipt.

## What to change or subtract first, as controlled prototypes

1. **Reduce repeated exact crossing-query setup.** `countRouteCrossings` already has a conservative bbox broad phase, but each surviving pair calls general `countPolylineCrossings([{points}, {points: other.points}])`, rebuilding segment objects, sorting, allocating location maps/string keys and dedup structures. Reuse precomputed immutable segment data for unchanged routes within one route-context revision; consider an exact pairwise specialization or scratch storage. Preserve subdivision/retracing deduplication, endpoint/tangent incidence, numerical tolerances, proper-crossing semantics and deterministic order. Crossings are not just boolean segment intersections. A count cap is only valid when a caller provably needs a threshold; retain full exact totals for public metrics.
2. **Reduce lane-scan work, separately.** First-only `collectLaneBlockers` CPU cost points toward precomputed obstacle extents, label bounds, collinear segment indexes or conservative range filtering. This is a computation target, not primarily an allocation target. `tryZRoute` mutates route/label state when a candidate is accepted, so an index or cached crossing count must invalidate/update on those changes; results cannot be reused blindly across the whole render.
3. **Instrument attempted versus winning reroutes before pruning them.** A source-only ablation of `tryZRoute` or one candidate family can bound cost, but removes repair behavior and is not an equivalent renderer. Compare final crossings, hard node/label defects, certificates, bends and retained adversarial seeds before considering a shipped reduction. This is better grounded than removing all cyclic-order trials because a flat `countPolylineCrossings` frame looked like cycle-search scoring.
4. **Make warm drawing cheaper without reintroducing full SceneDoc.** Split mark construction/leaf validation, SVG serialization, fragment ancestry flattening and native paint geometry inspection. Repeated `retainedNativeDrawing` frames mostly run first-time drawing for each fresh request/layout identity; they do not show the cache lookup as expensive. Explore immutable internal artifact reuse or less intermediate representation only with complete appearance/options/provenance dependencies. Keep leaf admission and paint/security contracts.
5. **Defer or reuse immutable digest-input preparation if safe.** Flow's request-resolution subtree suggests measuring `admitRenderContractDigestInput`, immutable snapshots and canonical preparation independently. Because later caller mutation can alter deferred data, moving snapshots later requires preserving the original input snapshot semantics; simply retaining mutable objects would be incorrect.
6. **Avoid repeated SVG scans/copies only with byte-identity proof.** Distinguish final security, envelope checks, color inlining and budget scans, measure their exact input bytes and cache hits. Existing exact-string inspection caching is real; preserve the final security boundary after transformations. The profiles justify reducing redundant work, not deleting required checks.

The next acceptance criterion is unchanged output/certificates and a stable uninstrumented paired improvement under the existing qualification harness, including fresh holdouts and unchanged public consumption. None of these profiles demonstrates a shipped improvement or universal parity with ELK.
